First, an important distinction

The Z80 ROM already did floating point in software. Our RV32 build now does too, using custom integer routines instead of the compiler's generic floating library. SINGLE has a 24-bit significand; DOUBLE has 53 bits split across two 32-bit registers. The CPU simulator implements no floating-point instructions.

Decoding EXP, rather than translating instructions

At ROM address 1439h, the Z80 saves the argument, multiplies by log₂(e), floors it, and builds a remainder. Functionally, this is:

k = floor(x * log2(e)) + 1
r = k * ln(2) - x
EXP(x) ≈ P(r) * 2^k       where P(r) approximates exp(-r)

Native DOUBLE algorithm

int k = floor_word(x * LOG2_E) + 1;

/* Keep the low remainder bits. */
double r = k * LN2_HI - x;
r = r + k * LN2_LO;

/* Degree 17, 18 coefficients. */
double y = polynomial(r, coefficients, 18);

/* Exact powers; underflow rounded last. */
return scale_by_power_of_two(y, k);

The C is compiled to RISC-V instructions. There is no Z80 register set, flag emulation or emulated 64 KB memory in the functional interpreter. Source comments pair the decoded algorithms with verified ROM addresses.

Why more coefficients help

The old table was designed for roughly SINGLE precision. Merely storing those numbers as DOUBLE preserves their old approximation error. The revised DOUBLE path uses exact-rounded coefficients for 1 − r + r²/2! − … − r¹⁷/17!. Over the reduced interval, the mathematical remainder is below 3×10⁻¹⁹; floating arithmetic adds its own rounding error.

This is a degree-17 Taylor polynomial with an error bound. It is not a newly fitted minimax polynomial, and it is not an input/output lookup table. A minimax fit could potentially achieve the same target with fewer coefficients; that remains an optimization to investigate.

Why the split ln(2) matters

For large x, k·ln(2) and x are nearly equal. Subtracting two already-rounded large numbers can erase the small remainder we need. We use (k·ln2_hi − x) + k·ln2_lo: the high product is exact over this k range, and the low part restores the missing information. A better polynomial alone would not repair bad range reduction.

Replacing generic floating helpers saved 1,724 bytes in the compact image. It did not explain the whole gap. These figures exclude ELF headers, browser code, heap, stack and BSS. The new interpreter still has fewer features than Level II, so this is not a feature-equivalent size victory.

Z80 INC A and ADD A,B each fit in one byte. Base RV32 equivalents usually take four bytes, or two bytes with suitable compressed encodings. RV32 can do more work per instruction on a 32-bit value, but that does not automatically make the whole interpreter smaller. Our parser, executor, conversion and storage routines also need further size work.

What is—and is not—validated

Custom integer arithmetic passed more than 1.8 million exact hardware comparisons. DOUBLE EXP passed 4,725 high-precision vectors on the host and actual RV32 under QEMU. The browser simulator boots the same freestanding ELF images and runs their custom arithmetic instructions. None of these sampled tests proves every possible IEEE result is correctly rounded.

Only DOUBLE EXP received this higher-accuracy polynomial. LOG, SQR/power through LOG and the trigonometric functions still have inherited approximation limits. SINGLE retains its ROM-derived coefficients. MBF bit compatibility, dynamic rounding modes and floating exception flags are not claimed.
